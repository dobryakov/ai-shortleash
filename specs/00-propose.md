ТЕХНИЧЕСКАЯ СПЕЦИФИКАЦИЯ НА РАЗРАБОТКУ АВТОНОМНОГО АГЕНТА РАЗРАБОТКИ (AUTONOMOUS TDD RUNNER)

1. ОБЩИЕ ПОЛОЖЕНИЯ И ЦЕЛЬ СИСТЕМЫ
Система представляет собой CLI-утилиту для Linux-сервера, предназначенную для полностью автономного выполнения одиночных задач по программированию на основе текстового описания и текстовых критериев приемки. Главные приоритеты: минимальная стоимость выполнения за счет использования недорогих моделей через OpenRouter API, изоляция выполнения в Docker-контейнерах, защита от подгонки тестов под баги (reward hacking) и жесткий контроль финансовых расходов с остановкой или эскалацией на человека (HITL) только в нештатных ситуациях.
2. ТЕХНОЛОГИЧЕСКИЙ СТЕК

* Язык управляющего оркестратора (Host): Python 3.11+
* Движок редактирования кода внутри песочницы: Aider (установленный в базовый Docker-образ, запуск в headless-режиме с флагами --yes-always и --no-auto-commits)
* Среда изоляции: Docker Engine (запуск контейнеров через Docker CLI или Python Docker SDK)
* LLM-провайдер: OpenRouter API (использование Provisioning API для выпуска лимитированных ключей и Chat Completions API)
* Система контроля версий: Git (обязательное наличие git-репозитория в целевом проекте)

3. ВХОДНЫЕ ДАННЫЕ И ИНТЕРФЕЙС ЗАПУСКА (CLI)
Запуск осуществляется одной командой из терминала хоста:
agent-run --project /path/to/repo --task /path/to/task.md --budget 0.50 --max-iter 8

Параметры запуска:
--project: путь к директории с исходным кодом проекта (должен быть инициализирован git).
--task: путь к текстовому файлу в формате Markdown, содержащему описание задачи, контекст/ограничения и текстовые критерии приемки.
--budget: максимально допустимый расход в долларах США на данную задачу (по умолчанию 0.50).
--max-iter: максимальное количество итераций цикла разработки (по умолчанию 8).
--keep-tests: флаг, определяющий, оставлять ли сгенерированные тесты в проекте после завершения или удалить (по умолчанию false — удалять временные артефакты перед финальным коммитом).

4. АРХИТЕКТУРА И СТРУКТУРА ДИРЕКТОРИЙ
Система состоит из двух уровней:
Уровень 1 (Host Orchestrator): Python-скрипт, работающий на хост-машине. Управляет Git, выпуском ключей OpenRouter, запуском Docker-контейнеров, проверкой лимитов, детектором зацикливания и нотификациями.
Уровень 2 (Worker Sandbox): Эфемерный Docker-контейнер на базе образа dev-agent-sandbox:latest, содержащего Python, Node.js, Git, Aider и стандартные тест-раннеры (pytest, jest и т.д.).

Временная структура внутри целевого репозитория во время работы:

* .agent/ (добавляется в .git/info/exclude хостом до старта, чтобы не засорять статус гита)
* .agent/prompt.txt (текущий промпт для Aider)
* .agent/run_tests.sh (скрипт запуска тестов, сгенерированный на Фазе 1)
* .agent/state.json (телеметрия: потраченный бюджет, номер итерации, хеши ошибок, статус)
* tests/acceptance_generated/ (изолированная директория для автотестов, созданных по критериям приемки)

5. АЛГОРИТМ РАБОТЫ (ТРЕХФАЗНЫЙ ПАЙПЛАЙН)

Предварительный этап (Init):

1. Проверка чистоты рабочего дерева git (git status). Если есть незакоммиченные изменения, работа прерывается с ошибкой.
2. Создание новой рабочей ветки agent/task-.
3. Запрос к OpenRouter Provisioning API для создания временного API-ключа с жестким лимитом расходов, равным параметру --budget.
4. Запись исключений .agent/ и tests/acceptance_generated/ в .git/info/exclude.

Фаза 1: Проектирование и генерация тестов (Test Architect)
Цель: превратить текстовые критерии приемки в исполняемый код тестов до написания основного кода (TDD Red Phase).

1. Проверка однозначности (Pre-flight check): оркестратор отправляет текст task.md и структуру файлов проекта (tree) дешевой модели (например, google/gemini-2.0-flash-001). Если критерии приемки противоречивы или неполны, модель возвращает JSON со статусом AMBIGUOUS и списком вопросов. Оркестратор выводит вопросы в stdout (и опционально в Telegram) и завершает работу (HITL).
2. Генерация тестов: оркестратор запускает Docker-контейнер с Aider на сильной модели (например, anthropic/claude-3.5-sonnet или deepseek/deepseek-r1) с доступом на запись только к tests/acceptance_generated/ и .agent/run_tests.sh. Промпт требует написать автотесты на каждый пункт критериев приемки и сформировать скрипт запуска .agent/run_tests.sh.
3. Валидация тестов (Red Phase Check): оркестратор запускает .agent/run_tests.sh внутри контейнера.

* Ожидаемый результат: тесты падают с ошибками логики (AssertionError, HTTP 404/500 и т.п.), так как функционал еще не написан.
* Если тесты падают из-за синтаксических ошибок в самих тестах или некорректных вызовов тест-раннера, оркестратор дает Test Architect до 2 попыток исправить сами тесты. Если тесты так и не запускаются корректно — остановка и HITL.

Фаза 2: Цикл разработки кода (Coder Loop)
Цель: написать код, который пройдет все существующие тесты проекта и сгенерированные тесты приемки.
Запускается цикл от 1 до max-iter:

1. Проверка бюджета: запрос текущего расхода по временному ключу через GET /api/v1/auth/key. Если расход >= budget — остановка и HITL.
2. Выбор модели (Каскадная маршрутизация):

* Итерации 1–3: дешевая быстрая модель (deepseek/deepseek-chat или qwen/qwen-2.5-coder-32b-instruct).
* Итерация 4 или при повторении одной и той же ошибки 2 раза подряд: переключение на модель среднего/высокого уровня (anthropic/claude-3.5-sonnet).

3. Запуск Worker-контейнера:

* Корневой каталог проекта монтируется в /workspace в режиме чтения и записи (rw).
* Каталоги /workspace/tests/acceptance_generated и /workspace/.agent монтируются поверх в режиме только для чтения (ro), чтобы модель физически не могла подделать или удалить тесты.
* Файл .env перекрывается пустым устройством /dev/null в режиме ro для защиты секретов.
* Aider выполняет правку кода по промпту, содержащему задачу и лог ошибок с прошлой итерации.

4. Верификация: оркестратор запускает в контейнере .agent/run_tests.sh (включающий как старые регрессионные тесты проекта, так и новые тесты из tests/acceptance_generated/).

* Если exit code != 0: берется хвост вывода (последние 3000 символов stdout+stderr), вычисляется MD5-хеш ошибки. Если хеш совпадает с предыдущим 3 раза подряд (даже после повышения класса модели) — фиксация тупика (Stuck Loop), остановка и HITL. Иначе переход на следующую итерацию с передачей лога ошибки в промпт.
* Если exit code == 0: переход к Фазе 3.

Фаза 3: Семантическая приемка (Spec Judge)
Цель: проверить соответствие кода тем текстовым требованиям, которые невозможно покрыть автотестами (архитектурные ограничения, стиль, отсутствие костылей).

1. Оркестратор собирает полный git diff текущей ветки относительно базовой.
2. Отправляет запрос (без Aider, напрямую в OpenRouter API) на модель с большим контекстом (google/gemini-2.0-flash-001), передавая исходный task.md и git diff.
3. Модель должна вернуть строгий JSON: {"passed": bool, "issues": [str]}.
4. Если passed == false: оркестратор формирует фидбек из списка issues и возвращает управление обратно в Фазу 2 (на следующую итерацию цикла).
5. Если passed == true: переход к завершению.
6. ЗАВЕРШЕНИЕ РАБОТЫ И ОЧИСТКА
7. Опционально - удаление временного API-ключа в OpenRouter (или его отзыв).
8. Если флаг --keep-tests не установлен, директория tests/acceptance_generated/ удаляется. Директория .agent/ удаляется в любом случае. Очищается .git/info/exclude.
9. Все изменения коммитятся в рабочую ветку agent/task- с автоматическим сгенерированным commit message и отчетом о потраченном бюджете.
10. В stdout выводится финальный отчет: статус SUCCESS, имя ветки, количество итераций, точная сумма расходов в долларах.
11. ТРЕБОВАНИЯ К БЕЗОПАСНОСТИ DOCKER-ПЕСОЧНИЦЫ
12. Контейнер запускается с флагом --rm (полное удаление после завершения шага).
13. Ограничение ресурсов: --memory="2g" --cpus="1.5" для защиты хоста от зависших процессов или утечек памяти в сгенерированном коде.
14. Файловая система контейнера вне /workspace монтируется как --read-only с выделением --tmpfs /tmp:rw,noexec,nosuid,size=512m.
15. Сетевая изоляция: контейнер работает в выделенной bridge-сети с правилами iptables на хосте, запрещающими доступ к локальным интерфейсам сервера (127.0.0.1, приватные подсети Docker/LAN) и разрешающими исходящий трафик только по портам 80 и 443.
16. Изоляция секретов: реальные файлы .env, ключи SSH и токены на хосте никогда не пробрасываются внутрь контейнера.
17. СЦЕНАРИИ ЭСКАЛАЦИИ НА HITL (HUMAN-IN-THE-LOOP)
При возникновении любого из 4 условий оркестратор сохраняет текущее состояние в .agent/state.json, оставляет рабочую ветку с текущим прогрессом (не удаляя код), отзывает временный ключ OpenRouter и завершает процесс с ненулевым кодом возврата и понятным диагностическим сообщением:
18. Неоднозначное ТЗ на этапе Pre-flight check (выводятся конкретные вопросы к автору задачи).
19. Исчерпание финансового лимита --budget.
20. Срабатывание детектора зацикливания (3 одинаковые ошибки подряд после эскалации модели).
21. Невозможность сгенерировать валидные запускаемые тесты на Фазе 1 за 3 попытки.
22. КРИТЕРИИ ПРИЕМКИ САМОЙ СИСТЕМЫ (ACCEPTANCE CRITERIA)
23. При подаче тестового репозитория и задачи с четкими критериями приемки утилита без участия человека создает ветку, генерирует тесты, пишет код, проходит проверку LLM-Judge и делает финальный коммит.
24. При искусственном занижении параметра --budget (например, 0.001 доллара) система гарантированно прерывает работу после первой же итерации, превысившей лимит, и возвращает статус остановки по бюджету.
25. При попытке модели внутри контейнера изменить любой файл внутри tests/acceptance_generated/ система блокирует запись на уровне ОС (Read-only file system).
26. При подаче заведомо невыполнимой задачи (например, тест требует несуществующий внешний сервис) система распознает повторяющуюся ошибку, повышает модель, убеждается в тупике и завершает работу с кодом эскалации HITL до исчерпания 10 итераций.
